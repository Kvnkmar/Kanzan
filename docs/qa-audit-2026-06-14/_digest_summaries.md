# Dimension summaries

## Multi-tenancy & tenant isolation (tenant-isolation) — 10 findings
CRM's multi-tenancy isolation is weakened by critical flaws: (1) InboundEmail uses a plain manager without automatic tenant scoping, creating cross-tenant dedup/query risks; (2) IMAP poller dedup checks messages globally without tenant filter (line 337); (3) tenant resolution happens after InboundEmail creation, leaving rows with NULL tenant in limbo; (4) some service paths (convert_to_ticket, some API calls) lack explicit tenant_context() wrapping, risking data leakage if downstream functions use implicit context. The system overall relies on developer discipline to add explicit tenant= filters everywhere InboundEmail is queried, and none of the uncommitted features (reminder-due, create-ticket-overrides) worsen this but also don't improve it. Tenant middleware and context managers work correctly when used, but edge cases (admin access, Celery task isolation) have minor gaps.

## Authentication (JWT / API key / session / SSO) (authn) — 9 findings
CRM's authentication system has solid fundamentals (timing-safe API key hashing, short-lived JWT, host-only sessions, signed handoff tokens) but carries three correctness risks: (1) fire_due_reminders lacks row-level locking and can fire duplicate notifications under concurrent worker contention; (2) DashboardView bypasses RBAC with IsAuthenticated-only permission; (3) Invitation tokens are reusable if races occur during acceptance. Two medium-severity issues around middleware context leakage in /admin/ and session-version adoption gaps also warrant attention. Overall, the system is production-ready with standard Django security practices, but these specific concurrency and permission gaps should be patched."

## Authorization & RBAC (authz-rbac) — 7 findings
CRM's authorization and RBAC system has several critical and high-severity issues: (1) a repeated ACTION_MAP key that silently overwrites permissions, (2) ~20 code sites using raw role instead of effective_role causing temp-role elevation to be inconsistently applied across API vs. frontend scopes, (3) IsTenantMember returning True when tenant=None creates a tenant-scoping bypass, and (4) no automatic cleanup of expired temporary roles. Feature A (reminder-due popup) is sound but Feature B (create-ticket overrides) is unreachable via the Hub API. Together these issues create privilege-escalation vectors and data-integrity risks, especially for temporary role grants which are silently ignored in critical filtering paths like ticket lists, analytics dashboards, kanban boards, and email auto-assignment.

## Inbox Hub access gate & permissions (inbox-hub-access) — 9 findings
The Inbox Hub access control and permissions system is fundamentally sound in its group-gating mechanism and row-scoping, with proper delegation to IsHubEmailAccessible and HubEmailPermission. However, several medium-to-high severity issues exist: (1) escalation_count increments even on illegal state transitions, (2) first_responded_at is never written despite being the key to SLA response-breach logic, (3) the partial SLA index excludes ESCALATED state, and (4) a feature parity gap exists between Hub and Emails create-ticket paths for override fields. Dead code (ESCALATION reason, unused API endpoints) and capacity-bypass vulnerabilities in manual claim/assign are lower-risk maintenance concerns. The group-gate itself is well-implemented and properly integrated across the API, page gate, and sidebar.

## Tickets CRUD, serializers, viewset actions (tickets-core) — 8 findings
The CRM Tickets CRUD surface has multiple data-integrity and security vulnerabilities centered on missing cross-tenant validation. The serializers validate only `status` and `queue` but NOT `contact`, `company`, `assignee`, or `pipeline_stage`, allowing attackers to link tickets to resources from other tenants via UUID guessing. Additionally, the model's assignee validation (clean method) is never invoked, and permission checks in bulk_action and get_queryset use raw role instead of effective_role, bypassing temporary privilege elevation. The codebase also carries dead code (F841) and unused imports. Overall, the RBAC and tenancy isolation are correct at the model/permission layer but bypassed at the serialization and viewset layer.

## Tickets services, SLA & business hours (tickets-services-sla) — 11 findings
The tickets services layer shows solid architectural foundations (dual-write logging, atomicity guards, per-tenant scoping) but has several critical and high-severity issues: (1) merge/split ticket locks are released immediately due to mis-chained .exists() calls, allowing concurrent data corruption; (2) SLA business-hours iteration silently truncates far-future deadlines without error; (3) first-response breach detection has a race condition between atomic stamping and task checks; (4) Feature B's legacy inbound-email path may lack atomic wrapping; and (5) several medium-severity gaps in priority-change SLA recalc, escalation dedup, and auto-close task safety. The webhook service and broadcast layer have minor concerns (hardcoded timeouts, insufficient error context). Overall code quality is solid, but the confluence of timing-sensitive SLA logic, concurrent locking, and multi-step operations requires urgent fixes in the high-confidence findings before production use of features involving large SLA durations, concurrent merge/split, or tight response windows.

## Tickets signals & dual-write logging (tickets-signals) — 8 findings
The tickets signals system exhibits multiple correctness and reliability issues across activity dedup, kanban card synchronization, and concurrent-write handling. The most critical findings are: (1) name-based kanban column matching breaks silently on renames, (2) concurrent pre_save state snapshots lack database locks and can see stale data, (3) kanban card ordering is racy under concurrent saves, and (4) resolved/closed timestamp semantics are lost by setting both to 'now'. The dedup window (2 seconds) is mis-documented as 5 seconds, and unused variables/swallowed exceptions hinder visibility. The system is broadly functional but fragile under high concurrency and column administration changes."

## Inbound email pipeline (SMTP/IMAP) (inbound-email) — 9 findings
The inbound email pipeline (SMTP/IMAP) is fundamentally sound for single-tenant operations but has a critical cross-tenant data integrity issue in the IMAP dedup logic. The IMAP poller checks for duplicate messages across all tenants rather than within a tenant scope, causing emails with the same Message-ID to be silently rejected for different tenants — a serious data loss scenario. Additionally, several medium-severity reliability and robustness issues exist around tenant resolution timing, watermark management, and recipient validation. The Feature A (reminder-due popup) and Feature B (create-ticket-overrides) implementations are well-designed with proper idempotency and transaction handling. Overall code quality is high with good logging and error isolation, but the cross-tenant dedup vulnerability and settings variable shadowing represent actionable improvements.

## Inbox Hub engine (routing/assignment/SLA/state) (inbox-hub-engine) — 11 findings
The Inbox Hub engine exhibits three critical data-integrity issues: (1) `first_responded_at` is never written, causing response SLA breaches to always fire on deadline without any way to mark SLA as met; (2) auto-escalation on breach has no deduplication, causing `escalation_count` to increment every task run; (3) the partial SLA index excludes ESCALATED state while the task scans it, degrading query performance. Additionally, `convert_to_ticket` and `dismiss_hub_email` bypass the state machine, and several role-evaluation inconsistencies exist. Feature B's overrides are unreachable via the Hub's own convert endpoint. Overall health is concerning for production: the SLA breach detection is fundamentally broken, escalation logic lacks safeguards, and architectural invariants (state machine, role consistency) are inconsistently enforced.

## Feature A — reminder-due popup (feature-a-reminder) — 7 findings
Feature A (reminder-due popup) is a well-designed 30-second beat task that surfaces can't-miss modal + audio + OS notifications when reminders become due. The F()-based re-arm watermark (due_notified_at) is correct, and the claim-first pattern prevents duplicate storms on send_notification failure. However, two critical issues emerge: (1) the NOTIF_TO_BADGE frontend mapping omits reminder_due, leaving the sidebar badge unupdated when the alert fires, reducing discoverability; (2) the lack of select_for_update creates a SELECT-then-UPDATE race if two Celery Beat schedulers run concurrently (single-beat architecture mitigates but not eliminates this). Additional medium-severity findings include stale recipient data between fetch and notification, and a redundant None-check on the recipient fallback. Overall, the feature is production-ready with minor UX polish and one deployment-safeguard recommendation."

## Feature B — create-ticket-from-email overrides (feature-b-overrides) — 8 findings
Feature B (create-ticket-from-email overrides) has solid validation and correct atomicity for the Hub path. Critical gaps exist: assignee lookup not strictly tenant-scoped, description truncation silent without user feedback, legacy path lacks atomicity for contact creation, Hub cockpit convert serializer never widened (5 fields unreachable), and zero direct API tests for the endpoint. Bare exception handler masks errors. Data integrity and test coverage gaps pose medium-to-high production risk.

## Notifications (in-app/email/WS) (notifications) — 9 findings
The Notifications subsystem is broadly sound with proper separation of concerns, transactional integrity, and permission enforcement. INTERNAL_ONLY_TYPES correctly gates agent-facing reminders from email; the WebSocket delivery is async-safe via group_send. However, there are moderate issues: (1) no race-condition guard when claiming reminder alerts (theoretical but possible if multiple workers overlap); (2) contact reply emails don't check the Contact.email_bouncing flag before queueing, wasting retries on known-bad addresses; (3) internal comment bodies broadcast tenant-wide via LiveBus without explicit role filtering (clients expected to filter, a documented latent info-leak); and (4) a minor unused-variable lint bug. Tests are green, INTERNAL_ONLY enforcement works, and Feature A (reminder-due popup) integrates cleanly into the notification pipeline.

## WebSockets / Channels consumers (websockets) — 7 findings
The WebSocket/Channels layer has three critical security issues: (1) VoIP call metadata is broadcast to all authenticated tenant members without role-based scoping, exposing phone numbers and linked contacts to viewers and unauthorized agents; (2) internal comments are broadcast tenant-wide with only documented-but-unimplemented client-side filtering, leaking sensitive agent notes to non-agents; (3) TicketPresenceConsumer bypasses documented ticket visibility rules (agent_visible_tickets_q) and allows any tenant member to join presence, revealing who is viewing tickets they should not access. Additionally, NotificationConsumer skips tenant membership verification, TicketPresenceConsumer lacks explicit close codes, and fire_due_reminders has a claim-first atomicity gap. The codebase is otherwise well-structured with proper auth checks in ChatConsumer and LiveEventConsumer, but these three findings represent material security and authorization violations."

## Contacts / Companies / Accounts / CRM (contacts-crm) — 9 findings
This audit of the Contacts/CRM scope uncovered several material data-integrity and reliability gaps: lead_score and health_score validation is defined in clean() but never invoked by API or scoring tasks (which use .update()), creating unbounded score risk; the contact_context_v2 cache has a fixed 60s TTL but is never invalidated when linked tickets change, serving stale open-ticket/CSAT aggregates; ContactEvent/last_activity_at updates bypass post_save signals via .update(), making timeline changes invisible to the live broadcast layer; score recalc tasks silently bypass signals, so clients never see computed score updates until page reload; and Company custom_data lacks the sync signal that Ticket/Contact have, orphaning company-level EAV rows. These are not causing active data corruption today, but represent latent vulnerabilities to stale reads, cache incoherence, and lost real-time updates.

## Knowledge base (knowledge) — 8 findings
The Knowledge Base module exhibits several critical and high-severity issues: PostgreSQL-dependent full-text search is completely broken on SQLite (the dev database), with no fallback despite API documentation claiming one; the KBVote voting system is vulnerable to ballot-stuffing attacks via session_key reuse when requests come from the same IP; two aspirational models (KBRevision, KBTicketLink) are fully migrated but never written to, indicating incomplete feature design. Additionally, there are code quality issues around confusing field names, unused dead code (PORTAL_VISIBILITY), missing input validation on search queries, and API documentation mismatches. Overall, the module is functional for basic article management and review workflows but has significant gaps in search, voting security, and feature completeness.

## Kanban boards (kanban) — 9 findings
Kanban audit complete: 4 critical issues (WIP races ×2, pipeline name-sync brittleness, effective_role bypass) and 5 medium-severity issues (migration clarity, soft-delete orphans, column-rename gaps, tenant validation, inconsistent WIP enforcement). Concurrency vulnerabilities can bypass WIP limits; name-based column syncing breaks silently on rename.

## Messaging / conversations (messaging) — 6 findings
The messaging system has three critical cross-tenant data isolation breaches: (1) mention resolution queries the global User table without tenant membership validation, allowing users to notify and leak IDs of users in other tenants; (2) direct message creation accepts any user UUID without validating tenant membership, allowing cross-tenant conversation mixing; (3) manual group conversation creation similarly lacks user_ids validation, enabling multi-tenant participant mixing. Additionally, Message.body allows blank values in the serializer despite being required at model level. WebSocket consumer hardcodes empty attachments while REST dynamically fetches them, causing inconsistency. Overall health: multi-tenant model undermined by insufficient participant validation at conversation creation and mention resolution scope-checking."

## Billing / subscriptions / Stripe (billing) — 7 findings
Audit of CRM billing system reveals two critical flaws: (1) VoIP plan flags completely absent from seeded plans, disabling VoIP for all new tenants; (2) OneToOne Subscription FK causes IntegrityError when tenants upgrade plans, blocking core workflow. Additional medium-severity issues: missing webhook idempotency tracking, unused require_feature decorator, and unprotected concurrent-beat race conditions in reminder firing. Overall system needs hardening for production.

## Analytics & exports (analytics-exports) — 9 findings
Analytics & exports stream audit reveals two critical security/reliability issues (DashboardView permission bypass, PDF export file-format mismatch, process_export_job transaction safety), three medium-severity business-logic gaps (agent_performance and reminder visibility leaks, Hub convert endpoint feature parity), and several low-severity code-quality concerns. Feature A (reminder-due popup) is well-implemented with proper task isolation and idempotent watermarking. Feature B (create-ticket overrides) works correctly but has a reachability gap where the Hub cockpit endpoint doesn't support the full override set."

## Attachments & file upload/download (attachments) — 10 findings
The attachments system has critical authorization gaps that allow unauthorized access to files. The primary issues are: (1) no object-level permission checks on attachment retrieval, allowing agents to download files from tickets/comments they don't have access to; (2) no authorization checks on upload targets, allowing agents to attach files to restricted objects; (3) direct webserver file serving without authorization proxying; (4) email attachment ingestion bypasses MIME validation and size limits; (5) listing/filtering attachments leaks metadata across tenant boundaries. Additionally, GenericForeignKey orphaning risks and redundant validation logic present data integrity and reliability concerns. The combined effect is a significant data leakage vulnerability where agents can access sensitive documents from restricted objects.

## Custom fields & agent presence (custom-fields-agents) — 9 findings
Custom fields subsystem has significant gaps: Company custom fields are never synced to the EAV table (data-integrity gap), visible_to_roles enforcement is broken (Q(isnull=True) never matches M2M), and role-visibility is entirely unenforced in the API layer. Agent presence suffers from timezone misalignment (working_hours uses server-local time, not tenant timezone), lack of transaction safety in the reaper (concurrent updates possible), and claim-first dedup in fire_due_reminders is architecturally flawed (stamp before send guarantees missed alerts on downstream failure). Several low-severity issues exist around EAV type coercion, multiselect JSON fragility, and performance (unindexed due_notified_at filter). Overall: two high-severity business-logic bugs (timezone + claim-first), multiple medium-severity data-integrity and reliability issues, and one critical data-sync gap (Company custom fields).

## Settings, secrets & infra config (settings-secrets) — 13 findings
CRM's settings, secrets, and infra configuration have critical vulnerabilities: (1) DJANGO_DEBUG split-default footgun where unset env var silently loads dev settings (ALLOWED_HOSTS=['*'], insecure cookies) instead of prod, a critical deployment risk. (2) Committed .env contains plaintext email credentials and webhook secrets, completely compromising inbound email security. (3) Missing CSRF_COOKIE_HTTPONLY protection leaves CSRF tokens readable by XSS attacks. (4) crm_voip queue defined but unconsumed, causing VoIP tasks to silently accumulate and never execute. Additional issues: crm_webhooks route unused (no billing tasks), Makefile omits crm-smtp from stop/restart, Beat crontab entries have timezone mismatch (UTC vs Asia/KL), JWT_SECRET_KEY defaults to SECRET_KEY, minor missing HSTS preload and cosmetic Makefile issues. The uncommitted reminder-due feature (A) lacks a performance index; the create-ticket-overrides feature (B) has incomplete serializer integration to the Hub endpoint.

## Frontend JavaScript (frontend-js) — 8 findings
The frontend JavaScript codebase is moderately healthy with solid sanitization practices (DOMPurify on HTML injection, textContent for user data) and good error handling in most places. However, there are 3 critical issues: (1) a dead link in the command palette (/contacts/new/ doesn't exist), (2) inconsistent WebSocket reconnection logic (notifications/ticket-feed give up after 10 attempts while live-connection retries forever), and (3) Feature B (create-ticket-overrides) only works via the Emails endpoint, not the Hub cockpit. Additionally, 13 of 14 JS files lack cache-busting query parameters, creating a stale-JS risk on production. Accessibility and memory management are generally good, though notes-panel and app.js could benefit from refactoring to event delegation.

## Templates & UI/UX (templates-uiux) — 10 findings
CRM's templates and UI/UX layer are well-structured with good Bootstrap integration and accessibility tokens. However, 10 issues were identified: keyboard accessibility gaps (password toggle, navbar icons), hardcoded z-index breaking CSS token system, semantic HTML mismatches (link styled as button), missing validation constraints, and dead macro code. Most are medium severity UX/accessibility issues rather than critical bugs, but password toggle inaccessibility and macro dead code warrant immediate action.

## Performance & database (performance-db) — 14 findings
CRM's database and performance tier shows moderate to high risk across querysets, indexes, and async patterns. Key findings: (1) Multiple N+1 query risks in high-traffic endpoints (notifications, analytics, inbox), (2) a critical partial-index mismatch on HubEmail SLA scans that can degrade performance at scale, (3) missing permission checks on DashboardView, (4) missing live-broadcast coupling for ContactEvent logging, and (5) Feature B widening of convert_to_ticket service without matching UI serializer. The codebase is generally well-structured with select_related/prefetch_related in most places, but gaps exist in notification/analytics views. SQLite concurrency issues affect dev/test only. No data-loss risks identified; most issues are performance or incomplete feature implementation.

## Data model & migrations integrity (data-model-integrity) — 9 findings
Critical and high-severity audit findings in CRM data models: (1) Ticket.clean() never called, allowing cross-tenant user assignment (Security/Critical); (2) NewsPost CASCADE delete silently purges announcements (Data Integrity/Critical); (3) fire_due_reminders race condition (Reliability/High); (4) Feature A migration stampede (Reliability/High); (5) unreachable validators (Business Logic/High). Nine total findings require immediate fixes.
